# Design decisions

Decisions made during the architecture phase. This document is the source of truth for any implementing agent.

## D1: Language coverage
**Decision**: Rust + TypeScript at launch.
**Why**: 27 Rust rules and 5 TypeScript rules already exist. Both are supported by ast-grep/tree-sitter. Covers the author's projects without adding complexity.

## D2: Target audience
**Decision**: Individual developers + CI/teams from the start.
**Why**: The tool must work as a local linter (fast, colored output) AND in CI pipelines (JSON/SARIF output, strict exit codes, --severity-threshold).

## D3: Distribution
**Decision**: cargo install only for v0.1.0.
**Why**: Users are Rust developers who already have cargo. Brew and binary releases come later.

## D4: Naming
**Decision**: slopguard.
**Why**: Descriptive, memorable, available on crates.io and GitHub.

## D5: Workspace structure
**Decision**: Multi-crate workspace from the start (slopguard-cli, slopguard-core, slopguard-rules).
**Why**: Clean separation of concerns. The core crate can be used as a library for programmatic integration. Rules are embedded at compile time. Each crate is independently testable.

## D6: Rule format
**Decision**: YAML superset of ast-grep format.
**Why**: 100% compatible with ast-grep (id, language, rule, severity, message). Slopguard adds: category, fix (textual suggestion), tests (should_match/should_not_match), and later ai_check. Users familiar with ast-grep can write rules immediately.

## D7: Configuration
**Decision**: slopguard.toml with hierarchical resolution (global ~/.config/slopguard/config.toml + project slopguard.toml + CLI flags).
**Why**: Familiar pattern (eslint, rustfmt). Global config sets personal defaults, project config enforces team standards, CLI flags override for one-off runs.

## D8: Output formats
**Decision**: Text (default, colored) + JSON + SARIF.
**Why**: Text for humans, JSON for scripting/dashboards, SARIF for GitHub Code Scanning / GitLab SAST native integration. JUnit was considered but dropped (legacy only).

## D9: AI integration
**Decision**: Ironflow SDK (LlmProvider trait + Operations). Multi-provider (Claude, OpenAI, ollama). Deferred to v0.2.0.
**Why**: Ironflow SDK already provides the multi-provider abstraction and operation tracking. Using LlmProvider + Operations gives structured, tracked AI calls. Not in MVP to ship faster and validate the AST layer first.
**Status**: shipped. The providers that landed are `api` (Anthropic or OpenAI over HTTP) and `cli` (the local `claude` binary); ollama was not implemented. An optional classifier axis was added later, see D35.

## D10: AI fallback behavior
**Decision**: Warning per skipped AI rule when no API key is configured.
**Why**: The user must know which rules are not running. A silent skip would give false confidence. An error would be too strict for optional features.

## D11: Exit codes
**Decision**: 0 = clean, 1 = findings, 2 = config error. --severity-threshold controls what counts as a finding.
**Why**: Standard linter convention. --severity-threshold error makes warnings non-blocking in CI.

## D12: Inline suppression
**Decision**: `// slopguard-disable-next-line` and `// slopguard-disable-next-line <rule-id>`.
**Why**: Same pattern as eslint-disable-next-line. Allows suppressing false positives without touching config. Rule-specific suppression is optional but recommended.

## D13: ast-grep integration
**Decision**: Embed ast-grep-core + ast-grep-config + ast-grep-language as Rust library dependencies.
**Why**: Zero external binary dependency. Full control over execution, error handling, and output format. The crates are MIT licensed, actively maintained (v0.43.0, 172k downloads/month), and designed for library use.

## D14: Rulesets
**Decision**: Three thematic rulesets: slop, security, correctness. Each can be enabled/disabled in slopguard.toml.
**Why**: Lets users opt into what they care about. A security-focused team might disable slop rules. A solo dev might enable everything. Categorization also improves the `slopguard list` output.

## D15: Rule testing
**Decision**: Inline YAML tests (should_match / should_not_match). `slopguard test` command validates them.
**Why**: One file per rule = the rule definition + its tests. No need to navigate between files. Forces every rule to prove it works. Should_not_match prevents false positives. External test files can supplement for complex multi-line cases.

## D16: Auto-fix
**Decision**: Textual suggestion only in v0.1.0 (fix field contains a human-readable message).
**Why**: Safe and simple. AST-based auto-rewriting comes in v0.3.0 once the rule format is validated.
**Status**: superseded by D31. `fix` stays a human message; rewriting lives in a separate `rewrite` field.

## D17: Cache
**Decision**: Deferred to v0.2.0. Cache AI results by file content hash + rule version in .slopguard-cache/.
**Why**: Not needed for AST-only scanning (already fast). Essential for AI rules to avoid redundant API calls and costs. In CI, the cache directory would be a CI cache artifact.
**Status**: shipped, and wider than planned: AST findings are cached per file content hash too (#17), with `--no-cache` and `--cache-dir` / `SLOPGUARD_CACHE_DIR`. AI results live under `<cache-dir>/ai/`.

## D18: License
**Decision**: MIT.
**Why**: Permissive, standard for Rust CLI tools, no friction for enterprise adoption.

## D19: CLI commands
**Decision**: scan, init, test, list.
**Why**: scan = core functionality. init = onboarding. test = rule validation. list = discoverability. Covers all essential use cases. `explain <rule-id>` deferred to post-MVP.
**Status**: `explain`, `stats` and `baseline` have since been added.

## D20: MVP scope
**Decision**: v0.1.0 is AST-only with all 34 builtin rules. No AI.
**Why**: Ship fast, validate the format and DX. AI is additive and can layer on top without breaking changes.

## D21: No dylint
**Decision**: Skip dylint (custom Rust compiler lints). Use AI for type-aware patterns instead.
**Why**: dylint requires nightly, couples to unstable compiler internals, and each lint is 100-300 lines of Rust with undocumented APIs. For 2-5 type-aware patterns, the maintenance cost exceeds the value. AI with targeted context achieves similar precision with 1% of the effort.

## D22: Patterns that need AI (cannot be AST-detected)
The following patterns are deferred to v0.2.0 (AI rules):
- **Intermediate Row struct**: e.g. `JobRow { status: String }` that mirrors `Job { status: JobStatus }` with weaker types, plus a manual conversion function. Needs cross-struct comparison.
- **Redundant .to_string()**: e.g. `status: job.status.to_string()` when `JobStatus` already derives Serialize. Needs type information.
- **SAFETY comment content validation**: the comment exists (AST-detectable) but is the justification real or hallucinated? Needs semantic understanding.
- **Doc-comment quality**: the comment exists and is non-trivial, but does it actually add information? Needs NLP judgment.
- **Cross-file trait with single impl**: a trait defined in one file with exactly one implementation in another. Needs cross-file analysis.

**Status**: the first four shipped as AI rules. The single-impl trait did not need AI after all: it shipped as a builtin cross-file rule, see D29.

## D23: Inline test code is filtered by an explicit rule flag
**Decision**: Rules opt into skipping `#[cfg(test)]` blocks with `skip_test_code: true`. The scanner locates those blocks on the tree-sitter AST (an `attribute_item` and the item it annotates) and drops the findings of opted-in rules inside them, after ast-grep matching. A textual brace scan was rejected: braces inside string literals or comments silently break it.
**Why**: `ignores` globs only filter whole files, but Rust convention puts unit tests inline in `src/`. Inferring the intent from the glob list (e.g. "contains `tests`") is fragile and invisible to rule authors. An explicit field keeps the YAML self-describing and lets a rule that must fire in tests (e.g. no-safety-hallucination) leave it off.

## D24: Baseline hash sans numero de ligne
**Decision**: un finding baseline est identifie par un SHA256 de `rule_id + chemin relatif au fichier baseline + matched_text + 2 lignes de contexte avant/apres, trimees`. Ni la ligne ni la colonne n'entrent dans le hash. Les doublons ne sont pas dedupliques : N occurrences identiques produisent N entrees, et le filtrage decompte (N baselinees, N+1 au scan -> 1 reporte).
**Why**: un hash incluant le numero de ligne invalide la baseline des la premiere insertion de code au-dessus, ce qui fait reapparaitre en masse des findings deja acceptes. Le contexte suffit a distinguer deux occurrences distinctes du meme pattern dans un meme fichier. La semantique de comptage evite qu'une occurrence baselinee masque une nouvelle occurrence identique.
**Cost**: modifier le code autour d'un finding baseline le fait reapparaitre. C'est assume : le code a change, la revue de ce finding aussi.

## D25: Config presets defined in code
**Decision**: `slopguard init --preset <default|strict|relaxed|ai>` renders its TOML from Rust in `slopguard-core::preset`. Fixed sections are string constants; the rule id lists (`strict`'s `enable`, `relaxed`'s `disable`) are computed from `load_builtin_rules()` at render time, sorted and deduped. No preset file ships on disk. The `strict` preset documents the warning severity threshold as a comment instead of a config key.
**Why**: a preset stored as data (a YAML or TOML file listing rule ids) drifts the moment a rule is renamed, retired, or flips its default, and nothing catches it. Deriving the lists from the shipped ruleset makes drift impossible by construction, and the unit tests round-trip every preset through `toml::from_str::<Config>` plus `is_rule_active` so a preset can never generate a config the scanner rejects. `--severity-threshold` is a `scan` flag with no `Config` key: adding one would mean making the flag optional and reworking scan resolution for a value that already defaults to `warning`, which is what strict wants. A comment in the generated file states the intent without inventing config surface.

## D26: Mode diff via git CLI
**Decision**: `slopguard scan --diff [--base <ref>]` resout la liste des fichiers changes en appelant le binaire `git` (`std::process::Command`), sans dependance `git2`/`gix`. Sans `--base`, la comparaison est `git diff HEAD` (staged + unstaged) ; avec `--base b`, c'est un diff trois points `b...HEAD`. Le filtre est `--diff-filter=ACMR` et la sortie est lue en `-z`. Les fichiers resultants sont passes tels quels au scanner via `scan_files` / `scan_files_cached`, sans parcours de repertoire, et un scan partiel ne purge jamais le cache.
**Why**: shell out vers `git` ne coute aucune dependance et utilise exactement la version de git que l'image CI embarque, y compris sa config (worktrees, submodules, `core.quotepath` neutralise par `-z`). Le diff trois points evite qu'une branche cible qui a avance fasse remonter des findings sans rapport avec la MR. `ACMR` exclut les suppressions (il n'y a plus rien a scanner) et rapporte les renommages sous leur nouveau nom. La liste explicite permet de scanner un fichier change meme s'il est cache ou gitignore, ce qu'un `WalkBuilder` refuserait. Enfin, purger le cache sur un scan partiel evincerait toutes les entrees encore valides des fichiers non regardes, et le scan complet suivant repartirait de zero.
**Cost**: les fichiers untracked ne sont pas inclus, puisque `git diff` ne les voit pas : il faut `git add` un nouveau fichier pour qu'il soit scanne. `--diff` exige un depot git, sinon exit 2.

## D27: Severity escalation runs after the baseline and outside the cache
**Decision**: `[escalation]` compte les findings par `(fichier, rule id)` et passe les warnings du groupe en errors des que le seuil est atteint. Le calcul est un transform post-scan applique par la CLI, apres `apply_baseline` et avant l'evaluation du `--severity-threshold` et le rendu. Le cache de scan et les hashs de baseline ne stockent jamais la severite escaladee. L'escalade est d'un seul niveau : un finding deja en `error` compte dans le groupe mais n'est jamais modifie. La fonctionnalite est opt-in (`enabled = false`), avec `--no-escalation` pour la couper sur un run.
**Why**: la concentration doit se mesurer sur les findings reellement rapportes, sinon des findings baselines gonflent le compte d'un fichier deja accepte et font echouer la CI sans qu'aucun code n'ait change. Mettre la severite escaladee en cache ferait diverger un scan partiel (`--diff`, qui ne voit qu'une partie des fichiers) d'un scan complet, et rendrait le contenu du cache dependant de la config plutot que du seul contenu des fichiers. Un seul niveau (warning -> error) garde le modele previsible et borne : il n'y a pas de severite au-dessus de `error`, donc aucune escalade en cascade a arbitrer. Enfin, l'escalade peut faire passer un run warnings-only de exit 0 a exit 1 sous `--severity-threshold error` : c'est l'interet de la fonctionnalite, et la raison pour laquelle elle est desactivee par defaut.
**Cost**: le compte est par fichier, donc un pattern etale sur dix fichiers n'escalade jamais, meme s'il est massif au total. C'est assume : la cible est la concentration dans un fichier, pas le volume global, que `slopguard stats` rapporte deja.

## D28: File-level metric rules
**Decision**: a rule carries either an ast-grep `rule` matcher or a `metric` plus a `threshold`, never both. The four metrics (`file_lines`, `import_count`, `function_count`, `comment_ratio`) are computed directly on the parsed tree in `slopguard-core::metric`, outside ast-grep, and produce at most one finding per file, anchored at line 1 column 1, with `matched_text` set to the measured value and its unit ("547 lines"). Firing is strictly `value > threshold`, so `threshold: 500` does not flag a file of exactly 500 lines. Test cases are whole files: inline entries in `tests.should_match` / `should_not_match`, or fixture paths in `tests.should_match_files` / `should_not_match_files`.
**Why**: ast-grep matches nodes, not files. There is no node that represents "this file has 547 lines", so a metric cannot be expressed as a pattern and must be evaluated outside the matcher. Anchoring at line 1 is the only position a whole-file property can honestly claim; inventing a position (the last line, the widest function) would make the caret in the text output point at code that is not the problem. Strict `>` lets a threshold be read as "up to N is fine", which is how a size budget is written everywhere else. Snippet-based tests are useless for a metric: measuring a five-line snippet against a 500-line threshold proves nothing, so the fixtures are real files of the right size.
**Cost**: `// slopguard-disable-next-line` targets the line after the comment, so it can never target line 1: a file-level finding is not inline-suppressible. The escape hatches are the rule's `ignores` globs and `rules.disable` in config. Because `finding_hash` mixes `matched_text`, a baselined file-level finding reappears as soon as the measured value changes. That is correct (the file grew), but it means a baseline does not freeze a metric finding the way it freezes a pattern finding.

## D29: Cross-file rules
**Decision**: a rule carries either an ast-grep `rule`, a `metric` plus `threshold`, or a `cross_file` kind, never more than one. The kind selects builtin Rust logic; the YAML only supplies identity, severity, user-facing text and scope. The first kind, `single_impl_trait`, fires for a trait with exactly one declaration, exactly one concrete impl and no blanket impl anywhere in the scanned project. Traits are matched by **bare name** (last path segment, generic arguments stripped), so `impl fmt::Display for X` counts toward a local `Display` and `impl From<u32> for X` toward `From`; a name declared twice anywhere abstains entirely. Only textual `impl Trait for Type` headers count, so `#[derive(Trait)]` is invisible. A blanket `impl<T> Foo for T` suppresses the trait outright. Impls are counted in **every** scanned file, test code included, while declarations are filtered by the rule's `files` / `ignores` globs, `is_test_path`, and `#[cfg(test)]` membership recorded at extraction time. There is no special case for `pub trait` at a crate root. Each file's symbol contribution is stored in its cache entry, behind a bumped cache schema version, and `--diff` / `scan_files` collect contributions but never evaluate the pass.
**Why**: a single-implementor trait is a project-level fact; no per-file matcher can see it, so the scanner needs a second phase over an index built from the same parse that produced the findings. Bare-name matching is what a scanner without a resolver can honestly do, and abstaining on a homonym is how it stays quiet instead of guessing which `Repository` an impl meant. Counting impls in test code is the point, not a leak: a trait with one production impl plus a `#[cfg(test)]` mock is the legitimate "trait exists to be mocked" pattern, and letting the mock count as a second impl removes the dominant false positive. A blanket impl covers a whole family of types, so the trait is never an over-abstraction. Zero impls stays silent because the implementor is probably outside the crate. Symbols must live in the cache: a cached run that returned findings without them would see fewer impls than a cold one and invent findings on a trait it has already cleared, so the schema version is mixed into the rules hash to drop every pre-symbol entry. `--diff` sees only changed files, so its index is incomplete by construction and its impl counts would be wrong; collecting contributions anyway keeps the next full scan cheap.
**Cost**: the pass is only as good as name matching. Two unrelated traits sharing a name silence each other, a trait implemented through a macro that expands to an impl is not seen, and a re-export cannot be distinguished from a local declaration. `--diff` never reports a cross-file finding, so CI that only runs diff mode will not see this rule. A line-1 trait declaration is not inline-suppressible, the same limitation metric rules have, because `slopguard-disable-next-line` targets the line after the comment; `ignores` and `rules.disable` remain. The cache schema bump invalidates every existing entry once, so the first scan after upgrading is a cold scan.
**Update (2026-09-26)**: the single concrete impl must now target a struct, enum or union declared in the trait's own crate (the nearest `Cargo.toml` above the declaration). An impl for a foreign type, a type alias, or a type from a sibling workspace crate is an extension trait: Rust only allows inherent methods in the type's crate, so the rule's advice ("call the concrete type directly") is impossible there. The 2026-09-26 benchmark showed 16 of 21 findings were such traits (`VersionExt`, `RouterExt`, `RuntimeExt`, ...). Each file's contribution now records the implementing type's bare name and the types it declares, behind cache schema v4. Public traits meant for downstream implementors (`Executor`, `ParallelVisitor`) still fire, as decided above.
**Update (D39)**: partial scans now evaluate the pass over the whole project's index; the "`--diff` never reports a cross-file finding" cost above no longer holds.

## D30: In-process rules run behind a `RuleEngine` trait
**Decision**: the three in-process rule kinds (ast, metric, cross-file) each implement one `RuleEngine` trait in `slopguard-core::scanner::engine`, and the orchestrator iterates the registered engines instead of calling each pass by hand. An engine declares its `EngineScope` (`PerFile` or `Project`); `CompiledRules::engines()` builds the registry and partitions it by scope. `evaluate(&self, ctx: &RuleContext)` takes a `RuleContext` that is `File` (path, language, source, the single parsed tree, `#[cfg(test)]` ranges) for per-file engines or `Project` (the assembled symbol index) for project engines. The orchestrator parses each file once and hands every per-file engine the same tree; a per-file engine gates parsing through `applies_to_file`, and symbol collection is driven by `needs_symbols()` rather than by a hardcoded "has cross-file rules" check. Inline disable stays applied per finding at the point its source is already loaded (per file for per-file engines, per declaration file for the cross-file engine), not as a separate aggregate pass. The AI pass is deliberately **not** an engine: it stays orchestrated by `slopguard-cli`. Adding a kind (import resolution, clone detection) means adding an engine and, if project-level, setting `needs_symbols()`; the orchestrator does not change.
**Why**: every new rule kind used to mean rewiring `scanner::orchestrate` by hand, and the risk was that filtering (inline disable, dedup) would be applied inconsistently between passes. A single trait makes "register an engine" the only step, and the `File`/`Project` split in `RuleContext` is what lets one `evaluate` signature serve both a per-file matcher and a project-level index pass without giving up the single parse: ast and metric share the same tree, and the cross-file engine reads the index that per-file symbol extraction built. The AI pass is left out on purpose. It is async, needs an external provider, and runs a two-phase candidate flow across a crate boundary; forcing it behind a synchronous core trait would drag the provider, cache and concurrency into `slopguard-core` and buy nothing, since the CLI already partitions AI rules on `ai_check`. Keeping inline disable at the source, rather than a final aggregate pass, means a cache hit never has to re-read a file just to suppress a finding, so the cache format and its performance are unchanged. The refactor is behavior-preserving: the same findings, formats and exit codes, and the existing integration tests pass unmodified.
**Cost**: the two-scope `RuleContext` enum means each engine ignores the variant it does not handle, a small amount of boilerplate the compiler cannot prove exhaustive. Building the engine registry allocates a short `Vec<Box<dyn RuleEngine>>` per scan (twice: once per scan entry point), negligible against parsing. A future engine that needs neither a per-file tree nor the current project index (say, one that reads raw bytes) would need a third `RuleContext` variant, not just a new engine.

## D31: Autofix through a separate `rewrite` field, gated by `autofix_safe`
**Decision**: a rule carries its rewrite in a `rewrite` field (an ast-grep replacement template that may reference the matcher's metavariables), separate from the free-text `fix`. `scan --fix` applies it only when the rule also sets `autofix_safe: true` (default `false`). An optional `autofix_rule` narrows the nodes that get rewritten when detection has to be broader than the fix. `slopguard-core::fix` compiles each autofixable rule with its `rewrite` as the ast-grep fix and matches the source directly. It applies the same filters as detection: `skip_test_code`, inline disable, baseline membership. Overlapping edits are resolved greedily in position order, and the mutated buffer is matched again until a fix point is reached, with at most 10 iterations per file. `--fix` refuses to write when the scanned paths have uncommitted changes, unless `--allow-dirty` is passed. Outside a git repository the guard passes. `--dry-run` prints a unified diff, writes nothing and exits 0. After writing, the paths are rescanned from disk, and the exit code is 1 when findings remain. `should_fix` test cases (`before` / `after`) prove each rewrite in `slopguard test`. Two rules ship autofixable: `no-dbg-in-prod` and `no-unnecessary-clone`.
**Why**: at the time, about 55 rules already used `fix` as a human message ("Use X instead"). Repurposing it would have made every one of them a rewrite template overnight. A separate field plus an explicit opt-in guarantees that nothing is rewritten unless its author declared the change idempotent and meaning-preserving. Reusing the detection filters keeps `--fix` from touching code the user suppressed inline or accepted in the baseline. The fix point handles rewrites that expose a new match, without an unbounded loop. The clean-tree guard makes every rewrite reviewable and revertable with git, so slopguard needs no backup mechanism of its own.
**Cost**: detection and rewriting match independently. A rule whose `autofix_rule` is narrower than its `rule` reports findings `--fix` never touches (`dbg!(a, b)` is flagged but not rewritten because the rewrite would not compile), and those findings keep the exit code at 1. With only two autofixable rules, `--fix` clears a small share of findings for now.

## D32: Import resolution runs per file, outside the engine registry
**Decision**: a rule may carry a `resolution` kind instead of `rule`, `metric` or `cross_file`. The only kind is `unresolved_import`, shipped as one YAML per language. Imports are extracted from the file's parse: `use`, `extern crate` and `mod` for Rust, `import` and `require` for TypeScript. They are then resolved against the manifests found by walking up from the file. For Rust, that manifest is `Cargo.toml` (plain, dev and build dependencies, `[workspace.dependencies]`, `[target.*]`, the package's own name). For TypeScript, it is `package.json`, plus `tsconfig.json` for `paths` aliases. Rust resolves only the crate-root segment, which is also accepted when it names a standard crate (std, core, alloc, proc_macro, test), a `crate` / `self` / `super` keyword, or a `mod` declared in the same file. A TypeScript specifier resolves to a declared dependency, an existing relative file, or a Node builtin. There is no network access and no `cargo` / `npm` invocation. The extracted import list is cached with the file, but resolution runs again on every scan. Findings are anchored on the import line and honor inline disable, the baseline and `--diff`. Resolution stays silent when no manifest is reachable, as well as on statement-level `import type`, re-exports and tsconfig `paths` aliases. It runs after the per-file pass, outside the `RuleEngine` registry of D30, even though D30 listed import resolution as a future engine.
**Why**: invented imports are the most expensive kind of slop: the code does not compile, or it crashes at load time. No pattern can catch them, because the answer is in the manifest, not in the syntax. Reading only the manifests already on disk keeps the scan offline, deterministic and fast, whereas `cargo metadata` would mean network access and a full dependency resolution. Stopping at the crate root is all a scanner without a module resolver can honestly assert. Splitting extraction (cached) from resolution (always rerun) keeps the cache keyed on file content alone, while still letting a `Cargo.toml` edit clear a finding in an unchanged file. The engine registry caches per-file results wholesale, which is why resolution sits outside it. Unlike a cross-file fact, an import depends only on its own file and its manifests, so diff mode sees the complete picture.
**Update (2026-09-26)**: the 2026-09-26 benchmark found 38 findings on five repositories that compile, all false: Rust 2018+ lets a `use` start from any name in scope. A Rust root now also resolves when the file binds it (a `mod`, including one declared inside a macro body, the last segment or alias of another `use`, the parent of a `self` in a list; a name bound by the very `use` being checked does not count), when it starts with an uppercase letter (crates are lowercase, so it names an item), or when its module scope holds a glob import not rooted at std/core/alloc (the glob may have brought it in). Cache schema v4 drops the old extracted imports.
**Cost**: deep paths are never checked (`use serde::Nonexistent` passes), and aliased or type-only imports are never reported. Since the update, an invented crate imported inside a module with `use super::*;` is not reported either. A resolution rule has no inline `tests` block because a snippet has no manifest. Its coverage comes from `tests/fixtures/resolution` and the CLI integration tests, and `slopguard test` lists it as untested.

## D33: External rule sources from git or local paths
**Decision**: `[[rules.sources]]` declares either a git repository (`git`, with an optional `ref` and an optional `path` sub-directory) or a local directory (`path` alone). A `ref` without `git` is a config error. Git sources are fetched by shelling out to `git` (`init`, then `fetch --depth 1 <url> <ref>`, then a detached checkout of `FETCH_HEAD`). Each source gets its own directory under `<user cache>/slopguard/sources/<hash of url and ref>`, and `SLOPGUARD_SOURCES_CACHE` overrides that root. An existing checkout is refreshed on every run on a best-effort basis: when the fetch fails, the cached checkout is kept. `--offline` never fetches and fails when the cache is missing. Authentication is delegated to git. `SLOPGUARD_GIT_TOKEN` overrides it for https URLs by injecting the token into the transient fetch URL only, never into the persisted remote. External rules load like custom rules, go through `slopguard test`, and carry their provenance: `source` in `slopguard list` is `builtin`, the git URL or the local path. A rule whose (id, language) matches a builtin is rejected with an error.
**Why**: `custom_dirs` forced teams to copy YAML between repositories. Delegating to the machine's git provides ssh-agent, credential helpers and `~/.gitconfig` for free, which is the same reasoning as D26. Hashing url and ref together means two refs of one repository never share a checkout. The best-effort refresh keeps a scan green when the remote is down. Silently shadowing a builtin would change what a rule id means without anyone noticing, so a collision is an error. Keeping the token out of the persisted remote means it is never written to `.git/config`.
**Cost**: there is no lockfile, so a branch `ref` follows the remote and two runs can load different rules. CI that needs reproducibility has to pin a tag or a sha. An online scan pays one fetch per git source. The token is visible in the process arguments while the fetch runs. There is no `slopguard add` command yet, so sources are edited by hand in `slopguard.toml`.

## D34: Unused disable directives are judged against raw AST matches
**Decision**: `scan --report-unused-disable` turns every `slopguard-disable-next-line` directive that suppresses nothing into a synthetic `warning` finding in the `slop` category, with rule id `unused-disable`, anchored on the comment line. A targeted directive is unused when no raw finding for its rule lands on the next line. A blanket directive is unused when no raw finding at all lands there. "Raw" means the findings of every active rule before suppression, AI rules included at their AST pre-filter stage, before any model verdict. They come from a separate, uncached scan. The flag is off by default, and it only looks at the changed files under `--diff`. `unused-disable` is not a YAML rule, so `slopguard list` does not show it.
**Why**: judging consumption against the AI verdict would make the report depend on the provider, the model, the cache and the network, so the same directive would flip between used and unused from one run to the next. The AST candidate is deterministic, so a directive on an AI candidate counts as used, which is the conservative choice. The pass is uncached because the scan cache stores findings after suppression, and those cannot tell which directive consumed what. Keeping the flag opt-in leaves existing CI output unchanged.
**Cost**: a directive that suppresses an AI candidate the model would reject is never reported as unused. A directive that targets a rule disabled in the config is always reported, because that rule never runs. Enabling the flag adds a second, uncached pass over the scanned files.

## D35: Optional System One classifier for AI rules
**Decision**: when `[ai.classifier].enabled = true`, the AI phase replaces the generative confirmation with a `DecisionProvider`: Jev, through ironflow's `TypeSafeProvider`. The `direct` transport uses `TYPESAFE_API_KEY` and the `openrouter` transport uses `OPENROUTER_API_KEY`. Each candidate becomes a yes/no `noul` question built from `ai_check.prompt`, with the optional `if_true` / `if_false` criteria, and the answer is a probability. The candidate fires when `p >= threshold`. The threshold comes from `[ai.classifier].threshold` (default 0.7), and `ai_check.threshold` overrides it per rule. The raw probability is cached under a key built from the file content, rule id, instructions and model, and the threshold is applied after the cache. `ai_check.reason` is either `static` (the default: the finding carries the rule's note) or `generated` (the generative LLM writes a reason for each fired candidate). Only `ai-ssrf-unvalidated-url` and `ai-open-redirect-unvalidated` are `generated`. When no LLM provider can be built, a `generated` rule falls back to its static note. The classifier does not depend on `[ai].enabled`, but the LLM behind `generated` reasons does. A missing key produces a single warning and the AI rules are skipped. `--no-ai` skips the classifier too. `slopguard-ai` keeps the `provider-typesafe` feature off by default, and `slopguard-cli` turns it on.
**Why**: confirming a candidate is binary classification. Paying a generative model for it is slow and expensive, and the model's self-reported `confidence` is not calibrated, so it cannot serve as a threshold. A classifier returns a probability that can. Caching the probability rather than the verdict means retuning a threshold never invalidates the cache, which is the same reasoning as D27. Only relational rules (SSRF, open redirect) need a reason tied to the specific data flow, and a static note serves the others. The feature is strictly opt-in because Jev is a proprietary SaaS, and the deterministic, offline AST mode remains the base of the tool.
**Cost**: `generated` rules need two providers configured to get per-instance reasons. Threshold quality depends on the labelled fixtures in `tests/fixtures/classifier_calibration/`, and the calibration harness that uses them makes billable calls, so it never runs in CI.

## D36: Classifier requests are batched per context cluster
**Decision**: before the classifier is called, cache-miss candidates are grouped per file into clusters of overlapping context windows. `CONTEXT_RADIUS` is 25 lines on each side, down from 50. A cluster is cut when it reaches `[ai.classifier].batch_max_questions` (8) or `batch_max_state_lines` (200). Each cluster becomes one multi-noul `DecisionRequest`: the merged region is sent once as a line-numbered `state`, and questions are keyed `q0`, `q1`, ... with each instruction naming its candidate's line. The cache stays per candidate with an unchanged key, and the threshold is still applied per candidate. Concurrency is bounded per cluster. When a cluster fails, all its members are skipped for that run, without a per-candidate retry. `batch = false` restores one call per candidate. The generative LLM pass is not batched.
**Why**: when several rules matched the same area, the classifier used to receive nearly the same 100 lines once per candidate, even though the TypeSafe API already answers several questions in one POST. Keeping the cache per candidate means batching changes only the shape of the network traffic: a later run with a different cluster layout still hits the cache. The smaller radius halves the input per candidate. The LLM pass is left alone because its output is paid and large, and it only runs for fired `generated` candidates.
**Cost**: batching is not decision-neutral, because each question sees the merged region rather than its own window, so borderline candidates can flip. The calibration harness (`slopguard-ai/tests/calibration.rs`) measures this drift. A single network error drops every candidate of a cluster for that run.

## D37: Duplicate messages only count error values, not panics
**Decision**: `duplicate_error_message` collects the string literals of `bail!`, `anyhow!`, `eyre!`, `format_err!` and `ensure!` only (matched on the macro's last path segment). `panic!`, `unreachable!`, `todo!`, `unimplemented!`, `.expect()` and `.expect_err()` are no longer collected.
**Why**: the rule exists because a message copied across files cannot be traced back to its site. A panic prints its own `file:line`, so a repeated panic or `.expect()` message is still traced, and those messages are developer-facing invariants ("core missing"), not errors a user reads. An error value built by `bail!` or `anyhow!` carries no location: two sites with the same text are indistinguishable in a log. The 2026-09-26 benchmark reported 111 findings, mostly `.expect()` and `unreachable!` invariants; 29 remain, all duplicated user-facing errors in cargo.
**Cost**: a duplicated `Err(MyError::new("..."))` built without one of these macros is not seen, and `.context("...")` strings are not collected.

## D38: Assertion-free tests follow their helpers across the project
**Decision**: `no-assertion-free-test` moves from an ast-grep rule to the cross-file kind `assertion_free_test`. Each file contributes its unasserted tests (a `#[test]`-like function with no `assert`/`panic`, `?`, `.unwrap()`/`.expect()`, inline snapshot or `#[should_panic]`, with the bare names of everything it calls) and its helpers (every other function or `macro_rules!` that asserts or calls something, with the same call list). The evaluation computes, by bare name, the fixpoint of helpers that assert directly, call an asserting helper, or call a name listed in `[rules.options.no-assertion-free-test] assert_functions` (globs, `*` wildcard). A test is reported when none of its calls reaches that set. Only test code can vouch for a test: a helper inside `#[cfg(test)]`, in a test path (built-in layout or `scan.test_paths`), or in a test-support crate, meaning a local path crate that workspace manifests declare only under `[dev-dependencies]` (a normal or build dependency anywhere disqualifies it). A compile-only test (a body of item declarations and typed `let _: T = ..` bindings) is not recorded, and trybuild directories (`**/tests/{ui,fail,pass}/**`) are ignored. `matched_text` stays the whole function, as the AST rule reported it, so existing baselines still match. Options live in a typed `[rules.options]` table with `deny_unknown_fields`: an unknown rule id or key is a config error.
**Why**: after the D37-era fixes, 680 findings remained on the benchmark and a classification showed 646 of them delegated their checks: 407 to a helper of the same file, 239 to a helper elsewhere in the project, mostly cargo's `Execs::run()` from `cargo-test-support`. No per-file matcher can see that, and a same-file analysis would have left the shared test support reported. Restricting vouching helpers to test code costs little (33 remaining with any code, 41 with test code only, measured) and stops a production `fn new` with a precondition `assert!` from silencing every test that calls a `new`. Name matching errs toward silence: a homonym produces a false negative, never a false positive, which is the right side for a rule that was the benchmark's noisiest. The option covers what no analysis can see, a harness from a crates.io dependency, the way `assertFunctionNames` does for eslint-plugin-jest. Measured result: 680 -> 26 on the benchmark, every other rule unchanged.
**Cost**: the rule loses its inline YAML tests; it is covered by unit tests in `cross_file/assertion_tests.rs` and a CLI fixture, like the other cross-file rules. Every function with a call now lands in the per-file symbols (cache schema v5, about 5 MB of cache for cargo's 1373 files). Calls are matched by name without types, so a method call `.run()` is vouched for by any test-code `run` that asserts. Remaining findings are mostly real "does not panic" tests and compile-time bound checks written as calls (`is_send::<T>()`), which the compile-only exemption does not cover.

## D39: Partial scans evaluate cross-file rules over the whole project
**Decision**: when a scan targets files rather than directories (`--diff`, or explicit files as the pre-commit hook passes them with `pass_filenames: true`), the cross-file index is completed from the project each file belongs to: its nearest ancestor holding a `slopguard.toml` or a `.git`, walked with the usual ignores. Those index-only files go through the cache like the others (a miss is scanned in full and stored), contribute their symbols, and never report. Every project-level finding is then kept only when it lies in a scanned file. A file outside any project is not widened. A walk whose paths include a file no longer prunes the cache.
**Why**: until now `--diff` skipped the cross-file pass, and the pre-commit hook, which passes files as scan paths rather than through `--diff`, ran it over an index made of the committed files alone, so `no-single-impl-trait` could report a trait whose other impls were not in the commit. With `no-assertion-free-test` becoming cross-file (D38), keeping the old behavior would have removed it from pre-commit, where it matters most against generated tests, or made pre-commit disagree with CI. Building the full index costs about 70 ms on cargo with a warm cache (0.16 s against 0.09 s for one file). Only reporting findings in scanned files keeps a partial scan's output scoped to what was asked, and the verdicts are those of a full scan. Pruning on a file walk used to evict every entry but the given files, so every commit left a cold cache behind.
**Cost**: a partial scan now reads every file of the project to hash it, and parses the ones missing from the cache (1.1 s cold on cargo, once). A finding whose anchor sits outside the changed files is not reported even when the change caused it: adding the only impl of an unchanged trait does not fire `no-single-impl-trait` until the trait's file is scanned.

## D40: The scanned repository's slopguard.toml is untrusted
**Decision**: `load_config` takes a `ProjectTrust`, `Untrusted` by default. With an untrusted repo file, the user-only keys are removed from its table before it is merged over the global config: the whole `[ai]` table (provider, vendor, model, `api_key`, `concurrency`, `[ai.classifier]`) and `scan.cache_dir`. Each removed leaf key yields one `warning: ignored '<key>' in slopguard.toml` line on stderr, without its value. Before the merge, `rules.custom_dirs` and the `path` of local `[[rules.sources]]` from the repo file must resolve inside the repository: existing paths are canonicalized (symlinks included), missing ones are checked lexically (no `..`, absolute paths under the root), and an escape is a `PathOutsideRepo` config error. Git sources are not checked. `[ai].concurrency` must lie in `1..=64` in every config file, and the AI runners also clamp it. Cache invalidation only deletes regular files named like an entry (`<hex>[-<hex>].bin`) in a directory that holds the `rules.hash` manifest. `--trust-repo-config` (global flag) restores the previous behavior for the repo file; a `--config` file is chosen by the user and always trusted.
**Why**: CI runs slopguard on merge requests, so the repo file is attacker-controlled. Honoring it let a merge request turn on the AI pass or the classifier on the runner's credentials (billable calls that send source code to a SaaS), switch provider, vendor or model, supply its own `api_key`, set a concurrency that panics the semaphore (`Semaphore::MAX_PERMITS`), load rule YAML from anywhere on the runner, or set `cache_dir` to an existing directory whose content the next rules change would delete. Rule selection, ignores and output stay with the repo: they only tune what the scan reports, which is the repo's business.
**Cost**: a repository that configured AI or the cache dir in its own `slopguard.toml` now gets warnings and must move those keys to the runner's global config or pass `--trust-repo-config`. A repo that loaded rules from a sibling directory must pass the flag or use a git source. Disabling the `security` ruleset from the repo file is still allowed.
